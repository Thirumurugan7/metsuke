Layout explorations

Seven arrangements of the same editor. The content in each is identical, so anything that looks different between two of them is a difference of layout rather than of styling. Every page has a notes panel with the tradeoff and a couple of live toggles to push the layout around. The last one is drawn from how Zed actually works.

What Zed does that is worth taking

Their hero shot is an agent-first three column layout

Left is a list of agent threads grouped by repo. Middle is the conversation. The code editor is the right-hand column. Code is explicitly not the centre of the window, which is the same bet variant B makes, shipped by people who had to live with it.

Read from the actual page rather than the docs. The docs describe docks and panels and never mention that this is the arrangement they chose to show.

A thread carries its branch, its diff and its age

Every row in that list reads like Add vim motion for surround pairs · +23 −2 · 48m or ⑂ gpui-accesskit / main · 4m. Status is a coloured dot. You can see which runs are working, which are waiting and how big each change is without opening one.

Ours are called "claude" and "claude 2". This is the single cheapest improvement on the page: name the tab after the task and hang the branch and diff off it.

Tool calls are one-liners, and the prompt is a card

Their agent panel renders Read crates/gpui/src/element.rs and Search "accessibility" in crates/gpui/ as compact rows with an icon, then the reply as plain prose, with the user's message in a bordered box above.

That visual contrast between prompt, action and prose is most of why it reads well, and it is the one thing an xterm cannot do. It also means parsing the agent stream instead of printing it, which is the real cost.

Docks, not a fixed layout

Zed has three docks and every panel can be dragged into any of them. It also exposes bottom_dock_layout, choosing whether the bottom dock spans the window or stays contained so the side docks keep their full height. That single setting is most of variant D for two lines of CSS.

It also sidesteps the argument this whole page is having. Ship a sensible default and let people move things.

The multibuffer, pointed at the agent

Zed opens project search, find-all-references and diagnostics as excerpts from many files in one buffer you can edit directly, with changes syncing back to each file. For a normal editor that is a refactoring tool. For this one it is the review surface: every hunk Claude just wrote, in one scroll, editable in place, instead of clicking through a list of changed files.

This is the strongest idea on the page and the one I would build first. It is also the most work, because synced cross-file editing is not a weekend.

Centered layout as a mode

Zed's centered_layout just adds padding either side of the editor, ratio 0 to 0.4. Trivial to add, and it is the difference between reading a long file and squinting at one.

Where I would actually go

B for the shell, E as a view inside it

B fixes the real problem, which is that the agent has the smallest box on screen while getting most of your attention. E fixes the second problem, which is that reviewing an agent's work through a file tree is archaeology. They compose: put the timeline where the tree is, and keep the conversation as the spine.

Having looked at Zed properly, I would fold F into that too: build it on docks so the arrangement is the user's to change, and make the review multibuffer the thing a timeline entry opens into.

C and D are worth having as modes rather than as the default. D in particular is a setting, not a redesign: it is variant A with the terminal rotated.

Beyond layout

Diffs should arrive, not be gone looking for

When Claude edits a file you are not looking at, nothing tells you. A quiet inline strip at the top of the editor, "3 files changed while you were reading this one", with a click to review, would close the gap without stealing focus.

Give the token counter a rate, not just a total

561M tokens is a number nobody can feel. Tokens per hour, or the cost of the last task, is a number you can act on. The same panel could mark the moment a session's context is getting long, which is when quality starts to slip.

Let the preview element picker write code, not just messages

Right now picking an element sends Claude a note. The obvious next step is picking an element and jumping straight to the JSX that renders it. The selector is already exact; the source map is the missing half.

Permission prompts belong where your eyes are

Approving a tool call currently means finding the terminal and typing. Since the editor already knows a permission was asked, the answer could be two buttons on the floating alert itself, which is the thing you are already looking at.

One command palette instead of five menus

Open folder, run the project check, test the UI, switch model, change theme and pick a sound live in six different places. A single palette would make every one of them discoverable, and would carry the keyboard shortcut education for free.

The empty preview is the best onboarding surface you have

Before a dev server exists, that pane is a dead grey rectangle taking a third of the window. It could be showing the two commands that would start one, detected from the project's own package.json.

These are mockups, not the app. They live in design/ and import nothing from src/, so nothing here can affect the editor. The styling is a hand-built copy of the real chrome, close enough to judge layout by and not close enough to trust for pixel decisions.
